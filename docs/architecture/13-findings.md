## (c) Under-documented, and worth attention

Before this set, these were known only from the code or the scripts. Items marked ⚠ are risks, not just gaps in the docs.

1. ⚠ **No CI, and deploys come from a working tree.** CI and pre-commit hooks were deferred in Phase 00 and there is no `.github/`. `deploy-*.sh` builds whatever is on disk, uncommitted changes included, and tags the image with `HEAD`'s short SHA. Nothing proves a deployed image matches a commit or passed `pnpm check`. ([04 §4.3](04-deployment.md#43-release-path))
2. ⚠ **The internet-facing identity can change every channel's data.** `sa-web` has `storage.objectAdmin` on all three buckets and `bigquery.dataEditor` on the dataset, only so it can delete. `requireChannel` is therefore the only tenant boundary. Running deletion as a job under `sa-pipeline` would let `sa-web` drop to read-only on raw (for artifacts) and write-only on uploads. ([04 §4.2](04-deployment.md#42-trust-boundaries-and-identities))
3. ⚠ **Retries ignore the cause.** Above `withRetry`, Cloud Run and the workflow retry any failure, so `ReauthRequiredError` costs about 6 container starts and 90 s of waiting. A distinct exit code, or the workflow checking `status` before retrying, would stop that. ([09](09-flow-failure-retry.md))
4. **Eventarc fires for every object in the uploads bucket, including Soundcheck's own archives.** Each soundcheck writes `{channel}/soundcheck-youtube/…` or `{channel}/soundcheck-beats/…` there, and each write starts a `soundcheck` workflow execution that ignores the object. That is harmless but noisy and billed. Moving those archives to another bucket would stop it. ([07](07-flow-soundcheck.md))
5. **No monitoring beyond logs and the budget.** There are no alert policies, dashboards or error reporting in `infra/`. A failed build is visible only on the creator's screen and in Cloud Logging. The budget alerts (50, 90 and 100%) are the only alarms.
6. **Retention is undocumented.** Uploads expire after 30 days. The raw bucket (every API response, every Gemini answer, the model artifacts) and BigQuery have no lifecycle or expiration. Keeping raw data is deliberate (rebuilds without re-fetching), but nothing says how long.
7. **Workflow settings use two names.** The web app reads `WORKFLOW_CHANNEL_BUILD`, while `weekly_refresh` reads `CHANNEL_BUILD_WORKFLOW`, set by `deploy-workflows.sh`. The deployed `channel_build` still carries an unused `MIN_TRAIN_VIDEOS` variable (STATUS, Oct 16).
8. **The weekly refresh has a single point of failure.** If the pooled refit fails three times, no channel refreshes that week, and nothing alerts anyone. ([06 §6.4](06-flow-channel-build.md#64-weekly-refresh))
9. **Two dead ends in navigation.** "No channel yet" after a disconnect has no connect button, and **Model (Soon)** is a disabled tab with no plan behind it. ([12](12-screen-flow.md))
10. **Fixtures don't cover soundchecks.** `export-fixtures` exports no soundchecks, inputs or model artifacts (Phase 15 notes), so the soundcheck screens and simulate cannot be exercised in fixtures mode without hand-made files.
11. **Before this set, the Firestore document model, the IAM matrix and the timeout table existed only in code and scripts.** They are now in [02](02-containers.md#where-state-lives), [04](04-deployment.md#service-account-matrix) and [09](09-flow-failure-retry.md#93-timeouts-and-limits-in-one-place). Keep them current when [schemas/firestore.ts](../../packages/core/src/schemas/firestore.ts), the IAM scripts, or a timeout change.
