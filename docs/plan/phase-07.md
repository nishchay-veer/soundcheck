# Phase 07 — Timeline and training table

**Goal.** One BigQuery table where each row is a (channel, video, audience, bin) with its full feature vector and the measured hazard as the label. The TypeScript featurizer in `packages/core` computes every column, including the spline basis and interaction terms, so the Python fitter only ever reads a finished matrix and live predictions use exactly the same code.

**Depends on.** Phases 04 and 06. Day: Oct 6.

## Stack

- TypeScript in `packages/core/src/features`; columns as `Float64Array` (no dataframe library needed)
- `@google-cloud/bigquery` (NDJSON load jobs, plus one MERGE for `feature_specs`)
- Vitest and fast-check; one fixture generated by Python (numpy, scipy) for the spline cross-check
- Python EDA: `google-cloud-bigquery` and matplotlib (both also needed in Phase 08)

## Build

1. `features/timeline.ts`: `buildBins(video, durationS, channelCtx, mix) -> FeatureFrame`, where `FeatureFrame` is 100 rows by `FEATURE_SPEC.length` columns stored column-major. `video` is any extraction with `format`, `target_level`, `payoff_time_s` and beats (a stored `VideoBeats` qualifies). `mix` is the newcomer traffic mix, or null for subscriber and `all` rows. Bin i covers `[(i-1)/100 * D, i/100 * D)`. Every feature is overlap-weighted across the beats that intersect the bin. Beats are first stretched to tile `[0, D]`: a gap or overlap between neighbours splits at its midpoint, so shares always sum to 1.
2. Feature families (86 columns). Each is stored in the form the model uses it, because Python never computes a feature:
   - **Beat type shares:** fraction of the bin covered by each `beat_type` (`beat_<type>`, 21).
   - **Picture:** fraction by each `visual` value (`visual_<value>`, 6); `talking_head_share` (weighted mean, 1 to 5); `static_talking_head_share` (fraction in beats with `talking_head_share` 5 and at most 2 cuts a minute: a person to camera with almost no editing, standing in for the removed `talking_head_static` framing); `log1p_cuts_per_min` (of the weighted mean); `on_screen_text` share.
   - **Audio:** `music_bg` and `music_fg` shares, `silence` share (beats with empty transcript).
   - **Delivery:** `energy`, `assumed_knowledge`, `info_density` (weighted means), `speech_wpm` (transcript words spread evenly across each beat).
   - **Dynamics:** `log1p_secs_in_current_beat` at the bin midpoint; `log1p_static_run_s` (consecutive seconds of static talking-head beats up to the midpoint, crossing beat boundaries); `energy_delta` versus the previous bin (0 in bin 1).
   - **Narrative:** `has_open_loop` (beats are read in order up to the midpoint; a beat that answers an earlier question closes one, then a beat that raises one opens one); `before_payoff` (0 when there is no payoff time); `knowledge_gap` = `assumed_knowledge` minus the channel's median `target_level`.
   - **Position:** `is_first_bin`, `log_bin_seconds` (D/100), and `pos_b1` to `pos_b6`: a clamped cubic B-spline basis of the elapsed ratio at the bin midpoint, interior knots 0.25, 0.5 and 0.75, implemented with the Cox–de Boor recursion in `features/spline.ts`. The full basis has 7 functions; the first is dropped because the model has an intercept. `log_duration` is not a column: it equals `log_bin_seconds` plus a constant.
   - **Video level:** `format` one-hot, `target_level`.
   - **Audience mix and interactions (newcomer rows only; zero elsewhere):** `mix_search`, `mix_suggested`, `mix_browse`: shares within non-subscribers (summed over the raw traffic types in each bucket), each centered at the channel mean stored in `channelCtx`. A video with no reported newcomer mix gets the channel mean. Plus explicit interaction columns `ix_<feature>_<mix>` for the 6 content features named in Phase 08 (`beat_sponsor`, `beat_intro_branding`, `knowledge_gap`, `log1p_static_run_s`, `info_density`, `before_payoff`), each the clipped feature times the centered share. Computing interactions here keeps the model purely linear in the feature vector.
   - Every column except the interactions is clipped to the range in the spec.
3. `features/spec.ts`: `FEATURE_SPEC`, an ordered list of `{name, kind, clip}`, inside `FEATURE_SPEC_DOCUMENT` with the spline knots, the interactions, the numbers features are computed with (bins, static talking-head thresholds) and `FEATURE_REVISION`. It is the single source of truth for column order. `FEATURE_VERSION` is `feat-` plus the first 12 hex characters of the document's SHA-256; a test fails, naming the new version, when the spec changes without it. Bump `FEATURE_REVISION` when a computation changes but no column does.
4. Leakage list in the same module: views, watch time, average view duration and percentage, `rewatch_mass`, `rewatch_bumps`, relative retention, survival and hazard, segment counts, subscriber counts, likes and comments. A test asserts none of them is part of any column name. Traffic-mix shares also come from Analytics, but they describe where newcomers came from, not how they watched; they are the one exception, used only on newcomer rows as a scenario chosen at prediction time (Phase 08's estimated audiences).
5. `soundcheck features --channel UC… [--force]` (`apps/pipeline/src/commands/features/`):
   - Refuses unless the latest `extraction-quality-gate` report for the current `EXTRACTION_VERSION` (from any channel) passed.
   - Uses videos that are eligible for training, have beats from the current extraction, and have at least one complete curve.
   - For each video and audience in `all`, `subscribed`, `unsubscribed`, joins bins to hazards by bin index. `n_at_risk` = views for that audience times `s_mono[i-1]` (with `s_mono[0]` = 1), where `all` views are subscribers plus newcomers.
   - Writes `training_bins` rows: `channel_id`, `video_id`, `audience`, `bin`, `hazard`, `n_at_risk`, `video_views` (the audience's views), `feature_version`, `extraction_version`, `as_of` (the curve's data date), and `x` as `ARRAY<FLOAT64>` in spec order. They replace the channel's rows in one transaction.
   - Writes the spec to `feature_specs` keyed by version, once, with a MERGE, so Python can name the columns.
   - BigQuery cannot partition by a string column, so `training_bins` is clustered by channel and video.
   - Skips the write when the rows would be identical to the last run's (the step marker stores a fingerprint of them); `--force` rewrites.
6. EDA lives in Python, where plotting is easy: `uv run --env-file ../../.env soundcheck-modeling eda [--feature-version …] [--channel …]` reads `training_bins` and `feature_specs` and writes `docs/eda/<feature version>/README.md` with three plots. It covers rows per channel and audience, missing data (non-finite values, missing audiences, features that never vary), distributions, and each feature's correlation with hazard (Spearman, and Pearson weighted by viewers at risk), with content features ranked apart from position, video and mix features.
7. Tests:
   - Golden test: a hand-made 3-beat video with known expected bin values.
   - Property tests: beat-type and visual shares sum to 1 per bin and every column stays within its clip, on random videos; the full B-spline basis (with intercept) sums to 1 at every point.
   - Spline cross-check: `services/modeling/scripts/spline_fixture.py` writes basis values from `scipy.interpolate.BSpline` for 101 points to `tests/fixtures/spline.json`; the TypeScript basis must match within 1e-12.
   - Leakage test, version-hash test and determinism test (same input, byte-identical frame).

## Decisions and gotchas

- Bins are relative, so a 40-minute video has 24-second bins and a 5-minute video 3-second bins. `log_bin_seconds` lets the model compare hazards across videos.
- Bin 1 carries packaging effects (title and thumbnail mismatch). `is_first_bin` absorbs them so content features are not blamed.
- Storing `x` as an array keyed by spec version means adding a feature never needs a BigQuery schema migration.
- Predictions on a new cut must use the same channel context (median target level and mean newcomer mix) as training; `channelContext()` computes it from the training videos.
- On a small channel many columns never vary (37 of 86 on the test channel), so a fitter that standardizes columns must handle a standard deviation of 0.

## Do not

- Compute any feature in Python.
- Use any outcome-derived value as a feature.
